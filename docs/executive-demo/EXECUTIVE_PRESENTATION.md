## Slide 2 — The Hospital Problem

**Three converging pressures on every Saudi hospital today:**

1. **Clinician burnout from documentation load** — physicians spend an
   estimated **3+ hours per day** inside the EHR *(target, industry
   benchmark)*, much of it manual note-writing and re-keying data the system
   already has.
2. **NPHIES claim rejection** — industry-reported rejection rates of
   **12–18%** *(target, industry benchmark)* driven by ICD-10-AM ↔ SBS/SFDA
   code mismatches and missing pre-authorization, discovered *after* the
   claim is submitted, not at the point of care.
3. **Liability risk from generative AI** — every LLM-based clinical tool on
   the market today carries hallucination risk: a model can state a drug
   interaction, a dose, or a diagnosis that sounds authoritative and is
   simply wrong. In a regulated clinical setting, that is not a UX bug — it
   is a patient-safety and liability exposure.

*Speaker note: land on #3 last. It's the bridge into Slide 3 — the other two
tools solve #1 and #2; almost nothing on the market seriously solves #3.*

## Slide 3 — The Breakthrough Architecture

**Two systems, cleanly separated, working together:**

- **Ambient multi-agent interface** — a scribe agent listens to the
  encounter and drafts structured notes; a pharmacist agent, a consultant
  agent, and an NPHIES/billing agent sit alongside it, each specialized to
  one clinical or administrative concern.
- **Neuro-Symbolic Causal Reasoning Engine (NSCRE)** — a Neo4j knowledge
  graph holding the patient's medications, conditions, and lab results
  (the Patient-Specific Knowledge Graph, or PSKG), plus reference graphs for
  drug-interaction, renal-dose-safety, and NPHIES-necessity rules. Every
  clinical *fact* an agent surfaces is the result of a Cypher traversal
  against this graph — not a model's best guess.

**The split in one line**: agents *decide what to ask the graph and how to
phrase the answer*; the graph *decides what is true*.

*Speaker note: this is the architecture slide, not the trust slide — trust
is next. Here you're establishing that there are two distinct systems at
all, which most audiences assume is "just one AI."*

## Slide 4 — Factual Safety Guarantee

**How hallucination is designed out, not filtered out:**

| Layer | Job | Can it invent a fact? |
|---|---|---|
| NSCRE (Neo4j + Cypher) | Determine drug interactions, renal dose limits, NPHIES necessity | **No** — deterministic graph query, same input always produces the same output |
| DeepSeek (LLM) | Turn the graph's JSON result into a clean sentence for the clinician | **No** — explicitly prompted and scoped to reformat only; every fact it touches was already produced by NSCRE |

- If NSCRE finds **zero** findings, the language model is never even called
  — there is nothing to reformat, so no prose is generated at all.
- Every agent response carries its **evidence chain** back to the UI
  untouched — the same object NSCRE produced, byte-for-byte — so the
  language layer has no path to add, omit, or soften a fact in transit.
- This is verified in our own test suite as **object equality**, not a
  fuzzy or LLM-judged check: the prose can vary in wording, but the
  structured facts and evidence chain must match the graph's output
  exactly, every time.

*Speaker note: the "object equality" line is for the CTO in the room — it
tells them this isn't a policy, it's a property the test suite enforces on
every commit.*

## Slide 5 — Point-of-Care NPHIES Automation

**Claim-readiness checked before the order is even signed, not after
submission:**

- Real-time **ICD-10-AM ↔ SBS/SFDA** code matching against the documented
  diagnosis, at the moment an order is entered.
- Every order line carries a status badge:
  - 🟢 **Green** — code matched, necessity justified, ready to submit.
  - 🟡 **Yellow** — pre-authorization required; **one click** submits the
    pre-auth request without leaving the order screen.
  - 🔴 **Red** — no necessity rule links this order to the documented
    diagnosis; the system suggests the codes that *would* justify it,
    correcting the mismatch before it ever reaches the payer.
- The badge color is a **billing/paperwork state**, never a clinical
  severity signal — a deliberate design line that keeps this feature inside
  administrative automation, not diagnostic judgment.

*Speaker note: the last bullet pre-empts a scope question from the CMO —
say it before they ask it.*

## Slide 7 — Explainable AI: Evidence Chains

**Every clinical claim is one click from its source.**

A "Show Reasoning" / "View Evidence Chain" control sits on every agent
recommendation and every NPHIES badge. Clicking it reveals the **exact
graph traversal** that produced the claim — not a paraphrase, the literal
path:

```
Patient(id=...) → LabResult(eGFR=28) → Medication(name=Metformin)
                → Rule(flag=CRITICAL_OVERRIDE)
```

- Every node and edge in that chain is a real object the graph query
  returned — nothing rendered, nothing summarized by a model.
- This turns "trust the AI" into "verify the query" — a fundamentally
  different, and much easier, ask for a clinician or a compliance
  reviewer to say yes to.

*Speaker note: if only one slide gets remembered, this is the one — it's
the visual proof of Slide 4's promise.*

## Slide 8 — Enterprise Integration & Compliance

- **Deployment**: Saudi in-Kingdom cloud or full on-premises, clinician's
  choice — no requirement to send patient data outside the Kingdom or
  outside the hospital's own network.
- **Saudi PDPL compliance**: all patient data, audit logs, and derived
  graphs stay in-Kingdom by default; audit logging is append-only with
  hash-chain integrity, independently verifiable.
- **FHIR R4 interoperability**: standards-based integration with existing
  HIS/EHR systems via FHIR client + HL7 v2 adapter — this is an addition
  to the hospital's stack, not a replacement requiring a rip-and-replace
  migration.
- **NPHIES-native**: built against the live NPHIES FHIR sandbox from day
  one, not retrofitted.

*Speaker note: this slide exists to get IT/security sign-off in the same
meeting as clinical sign-off — don't skip it even in a clinically-focused
audience.*

## Slide 9 — Measurable Hospital ROI

| Metric | Target | Mechanism |
|---|---|---|
| Time per encounter | **-65%** *(target)* | Ambient scribe removes manual note-typing; order entry and claim-check happen inline |
| NPHIES claim rejections | **-85%** *(target)* | Point-of-care code/necessity validation before submission, not after |
| Hallucination-driven liability | **Zero** *(structural, not statistical)* | Facts are graph-sourced by architecture, not by model behavior that could drift |

**Why "zero" is different from the other two rows**: the first two numbers
are *targets* to be measured in a pilot. The third is a **structural claim**
— DeepSeek is never in the path between a patient fact and the graph that
owns it, by design, enforced by our own test suite. It isn't something a
future model upgrade could silently regress.

*Speaker note: don't let "zero" sound like marketing hyperbole — the
mechanism, not the number, is the argument. Point back to Slide 4.*

## Slide 10 — Pilot Roadmap: 30-Day Proof of Concept

| Week | Milestone |
|---|---|
| **Week 1** | Scoping + integration: connect to the hospital's FHIR/HIS endpoint (read-only), select 1–2 pilot departments (e.g. Internal Medicine + Cardiology), load department-specific NPHIES necessity rules |
| **Week 2** | Shadow mode: Veritas-Medica runs alongside existing workflow with synthetic/de-identified encounters; clinical + IT teams validate evidence chains against known cases |
| **Week 3** | Live pilot: opt-in clinicians use the VeritasShell for real encounters in the pilot department(s); NPHIES badge accuracy and time-per-encounter tracked from day one |
| **Week 4** | Measurement + go/no-go: compare pilot-department metrics (time per encounter, NPHIES rejection rate) against the department's own pre-pilot baseline; present findings and a scale-up plan |

**What the hospital needs to provide**: a FHIR-reachable read endpoint for
the pilot department's encounters, two clinician champions, and IT sign-off
per Slide 8.

**What we bring**: the platform, department-specific NPHIES rule loading,
and a dedicated implementation engineer for all four weeks.
